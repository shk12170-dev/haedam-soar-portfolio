# 2026-11-19 — 환경 버그 수정 (기동 시 재발 주의)

재기동 점검 중 발견해 고친 환경 측 문제만 기록한다(케이스 검증 결과는 2026-11-16과 동일해 생략).

## 1. pfSense 시계 3일 지연 → 경계 차단 탐지(S10) 실패의 진짜 원인

- 증상: pfSense가 Graylog로 보내는 `filterlog`(경계 차단)가 **과거 시각(11-16)**으로 찍혀, 탐지 창(최근 15분) 밖으로 빠졌다. 그래서 S10 3계층 중 `pfsense-block` 레이어만 상관되지 않아 S10 탐지가 발동하지 않았다. 포털 시계 기준인 S1·S4·S8은 영향 없음.
- 원인: pfSense VM 재부팅 뒤 시간 동기화가 안 돼 시계가 `date`상 `Mon Nov 16 21:50`에 멈춰 있었음(`/var/log/filter.log` mtime도 11-16).
- 조치: pfSense 시각을 호스트에 맞춰 교정.
  ```sh
  # host(KST)에서
  NOW=$(date +%Y%m%d%H%M.%S)
  ssh admin@10.10.30.1 "date $NOW"
  ```
- 확인: 교정 후 `.22`의 boundary 두드림이 현재 시각으로 OpenSearch에 수신(`rule:pfsense-block`, `pf_noise`/`pf_scope` 없음).
- 주의: **시계를 앞으로 크게 점프시키면 OpenVPN 터널/NAT 상태가 흔들린다**(아래 2번과 직접 연관). 기동 순서상 pfSense 시계를 먼저 맞춘 뒤 OpenVPN을 올리는 게 안전하다.

## 2. 포털 GELF 소켓 좀비화 → 포털 이벤트 전송 중단

- 증상: 포털이 HTTP는 정상 응답(404/401)하는데, 해당 `web.request`/`web-scan`/`login-bruteforce` GELF 이벤트가 Graylog에 도착하지 않았다. 20분간 포털 이벤트 1건뿐.
- 원인: 1번 시계 교정에 따른 OpenVPN 재연결로, 포털→Graylog GELF TCP(`10.250.0.2 → 10.250.0.100:12201`)가 **반쪽짜리**로 남았다. `ss`에서 `ESTAB`이지만 `Send-Q`에 4.5KB가 쌓여 배출되지 않는 상태(상대측 연결 상태가 재설정됨).
  ```
  ESTAB 0 4503 10.250.0.2:40602 10.250.0.100:12201 users:(("waitress-serve",pid=1418,fd=8))
  ```
- 조치: 포털 백엔드 재시작으로 새 GELF 연결 수립.
  ```sh
  ssh haedam@10.10.30.20 "sudo -n systemctl restart haedam-portal.service"
  ```
- 확인: 재시작 후 `.22` `login-bruteforce` 등 포털 이벤트가 다시 OpenSearch에 수신됨. 포털 VM 시계도 호스트와 일치(03:35Z).
- 일반화: **터널(OpenVPN)을 재시작하면 포털의 GELF 지속 TCP가 끊길 수 있다.** 터널 재연결 후에는 포털 백엔드도 재시작해 GELF를 다시 붙이는 것을 기동 체크리스트에 넣는다.

## 3. Wazuh 포털 에이전트 ID 재할당 010 → 001 (관찰)

- 포털 VM Wazuh 에이전트가 재등록되며 ID가 `010 → 001`로 바뀌었다(상태 Active, FIM 실시간, AR `s7-restore-ar` available).
- 규칙 기반 S7 자동 복구는 `active-response`의 `location:local`이라 **에이전트 ID와 무관하게** 보고 에이전트(001)에서 동작 → 영향 없음.
- 주의: n8n API 복구 경로(haedam-15)가 과거 `010`을 하드코딩해 참조한다면 그 보조 경로만 수정 필요. 규칙 기반(주 경로)은 정상.

## 기동 체크리스트 보강(제안)

1. pfSense 기동 직후 `ssh admin@10.10.30.1 date`로 시계 확인, 틀리면 호스트 시각으로 교정 — **OpenVPN 올리기 전에.**
2. OpenVPN(터널) 재시작을 했다면, 포털 백엔드(`haedam-portal.service`)도 재시작해 GELF 재연결.
3. Wazuh 에이전트 ID 확인(`agent_control -l`). S7 규칙 기반 복구는 ID 무관.
