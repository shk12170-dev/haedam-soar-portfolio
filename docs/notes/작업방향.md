### 2-1. 결정에 따른 주의점 (알고 가야 할 것)

1. **과제 문구와의 차이:** 공지는 5가지를 "각각 **컨테이너**로 동작하도록 구성(docker compose 등)"이라고 한다. pfSense를 VMware VM으로 두면 이 문구와 **정확히는 맞지 않는다.** 대응: README에 "pfSense는 FreeBSD라 공식 컨테이너가 없어 팀 구성과 같은 VMware VM으로 둔다"는 이유를 적고, **VM 설치를 README 단계 + `config.xml` 복원으로 재현 가능하게** 만든다. (강사가 문제 삼을 수 있는 지점이라 기록해 둔다.)
2. **강사 PC 재현:** 검사는 학원 PC에서 README대로 한다. 학원 PC에 VMware가 있어야 한다(팀 때 사용했으므로 있을 가능성이 높지만 **확인 필요**).
3. **공개 저장소 = 첫 push부터 외부 공개.** 따라서 **모든 push 전에 `secret_scan` 0건**을 강제한다(커밋 훅 또는 push 전 점검). 팀 저장소에서 반입하는 파일에 키·웹훅·내부 주소가 섞여 있을 수 있으므로, **반입 → 검사 → 첫 push** 순서를 바꾸지 않는다. 팀원 실명·GitHub 계정이 공개되므로 출처 표기 범위도 이 기준으로 정한다.
4. **6개 티켓 × 이틀:** 팀이 4명·3주 걸려 만든 것을 1명·2일에 재현하는 분량이다. 순서를 정해 **완주한 티켓부터 확정**하고, 못 끝낸 티켓은 "미완료·사유"로 정직하게 남긴다(실패 조건 위반보다 낫다).

**한 PC로 합칠 때 생기는 차이 (팀 조건과 완전히 같게는 안 되는 부분)**

1. **VPN 주소 `.3`과 `.100`이 같은 호스트에 있어야 한다.** 팀은 C와 D가 다른 PC라 각자 OpenVPN 클라이언트를 붙였다. 한 PC에서는 Windows 호스트에 OpenVPN 클라이언트 **2개**(team-c, team-d 프로필, 어댑터 2개)를 띄우고 Docker 포트를 각 주소에 묶어야 팀 주소가 그대로 유지된다. 동작은 시험해 봐야 안다.
2. **호스트가 pfSense LAN(VMnet7)에도 직접 붙는다.** 팀은 C·D가 학원망을 거쳐 B의 pfSense에 VPN으로 들어왔다. 한 PC에서는 VPN 클라이언트가 VMnet7(또는 NAT)을 통해 같은 PC의 pfSense에 붙는다. 경로는 다르지만 pfSense의 OpenVPN 규칙을 거친다는 점은 같다.
3. **메모리:** 팀 기획서 배정은 B VM 합계 약 7GB(pfSense 2·DB 2·Kali 2·외주 PC 1), A 포털 VM 약 4GB, C·D Docker 각 10~11GB였다. 한 PC 15.3GB에 모두 올리려면 VM을 줄여야 한다(아래 5절 2번).

## 5. 가장 먼저 풀어야 할 것 (차단 요인 → 위험 순)

0. ⛔ **BIOS에서 가상화 켜기 (사용자 작업, 재부팅 필요)**
   부팅 시 BIOS 진입(보통 `Del`/`F2`/`F10`, 제조사별) → `Advanced` / `CPU Configuration` → **SVM Mode = Enabled** → 저장 후 재부팅. 확인: `systeminfo`의 "Virtualization Enabled In Firmware: **Yes**".
   이것 없이는 아래 모든 작업이 불가능하다.
1. **설치:** VMware Workstation Pro 17(개인 무료), Docker Desktop(WSL2 백엔드), OpenVPN Community 클라이언트, Python 3.12, GitHub CLI.
   - **VMware와 Docker Desktop 공존:** Docker Desktop(WSL2)이 켜지면 Windows 하이퍼바이저가 올라가고, VMware 17은 그 위에서 **WHP 모드**로 돈다(동작하지만 느려질 수 있음). 둘을 같이 띄웠을 때 pfSense·포털 VM 기동 확인이 첫 스파이크다.
2. **메모리 예산 (15.3GB):**

   | 묶음 | 대략 |
   | --- | --- |
   | 묶음 | 팀 배정(기획서) | 이 PC 목표 |
   | --- | --- | --- |
   | Docker(WSL2): Graylog 스택 + Wazuh + n8n + 티켓 저장소 | C·D 각 PC 10~11GB | **9GB** (`.wslconfig`, 적용됨) |
   | pfSense CE 2.7.2 | 2GB | 1GB (Suricata 끄면 충분) |
   | DB VM (Ubuntu 24.04 Server, MySQL 8.4.11) | 2GB | 1GB |
   | 포털 VM (Ubuntu 24.04) | 3.8GiB | 1.5GB |
   | Kali 2026.2 | 2GB | 1.5GB (데스크톱 대신 콘솔 위주) |
   | Windows 자체 | — | ≈ 2GB |
   | **합계** | 4대 분량 | **≈ 16GB → 15.3GB 초과 위험** |

   대응 순서: VM 메모리를 위 목표값으로 → Kali 콘솔 모드 → OpenSearch heap 1g→768m → Wazuh indexer 1g→768m → `.wslconfig` 8GB. 그래도 부족하면 **시나리오별로 필요한 묶음만 켠다**(S7만 Wazuh 필수 등). 다만 검사 때 "5개 동시 동작"은 보여야 하므로 **동시 기동 1회 실측**은 반드시 남긴다.
3. **OpenVPN 경로:** pfSense OpenVPN 서버 ↔ 포털 VM·호스트 클라이언트가 팀 주소로 붙는지, GELF(TCP 12201)·syslog(514)·Wazuh(1514/1515·5514)가 통하는지.
4. **출발지 IP 보존:** 공격 VM → pfSense WAN 포트 포워드 → 포털에서 `src_ip`가 공격자 주소로 찍히는지(포털 IP 차단과 pfSense 차단이 같은 `src_ip`로 묶여야 S10이 성립).
5. **셀프 차단 방지:** 공격자만 막히고 정상 사용자·호스트(보호 대역)는 200 유지.
