## 3. 남은 한계와 더 개선하고 싶은 부분

- **S10 경계 차단:** pfSense 블록 테이블은 등록되지만 HTTP 새 연결은 막지 못한다(포트 포워드 규칙과 평가 순서 문제로 추정). 포워드 규칙 앞에 블록 규칙을 두거나 floating 규칙으로 옮겨 검증하고 싶다.
- **S12 판정 지표:** `/health` 2000ms 기준으로는 안전 부하에서 저하가 보이지 않는다. 정상 사용자 경로(`/login` 등)의 p95로 판정을 바꾸고, 차단·회복 경로를 실제로 발동해 보고 싶다.
- **원복 자동화:** 효과 확인과 해제는 사람이 했다(`haedam-50`은 dry_run 고정). 효과 확인 → 해제 → 티켓 기록까지 자동으로 연결하고 싶다.
- **S7 티켓 종료:** 닫기 가드가 격리 → 복구 2단계를 기대해 단일 복구 티켓이 `verified`에서 멈춘다. 가드에 복구형 티켓 경로를 추가해야 한다.
- **반복 실측:** 케이스당 1회만 완주했다. 목표는 3~5회 반복으로 MTTD·MTTR 분포를 내는 것이다.
- **새 PC 리허설:** README대로 빈 PC에 처음부터 설치하는 리허설을 아직 하지 않았다.

## 4. 느낀 점

- **분산을 한 PC로 모으면 보이지 않던 의존이 드러난다.** 팀 때는 "각자 PC에 원래 있던" 설정(외부 볼륨, 개인 Kali 스크립트, 손으로 만든 n8n 자격 증명)이 많았다. 혼자 다시 세우면서 그것들을 스크립트와 `.env.example`로 바꾸는 일이 작업의 절반이었다.
- **보안 로그의 기본은 시계다.** 가장 오래 걸린 장애 두 개(9시간 지연, 3일 지연)가 모두 시각 문제였다. 탐지 규칙보다 먼저 시계 동기화와 시간대를 점검해야 한다는 것을 몸으로 배웠다.
- **"동작한다"와 "증명된다"는 다르다.** 일지에 시각·건수·티켓 번호를 남기고 이 PC에서 직접 잰 값만 완료로 적는 원칙을 지키니, 발표 때 수치를 자신 있게 설명할 수 있었다.
- **자동 대응은 되돌리기부터 설계해야 한다.** 차단보다 해제·원복·오차단 확인이 더 손이 많이 갔다. 관찰 모드(dry_run) 기본값과 정상 출발지(`.100`) 확인을 모든 회차에 넣은 이유다.
