# 개선점과 느낀 점 (회고)

> 1인 재구현 과정에서 막혔던 지점을 **문제 → 원인 → 해결 → 결과** 순서로 정리했다.
> 근거는 [docs/journal](journal/)의 날짜별 기록과 git 이력이다.

## 1. 문제 해결 사례

### 1-1. S10 3계층 탐지가 발동하지 않음
- **문제:** 경계·스캔·로그인 3계층을 모두 입력했는데 S10 상관 이벤트가 생성되지 않았다. (S1·S4·S8은 정상)
- **원인:** pfSense VM 시계가 재부팅 뒤 **3일 지연(11-16 고정)** 돼 있었다. pfSense가 Graylog로 보내는 `filterlog`(경계 차단, `rule:pfsense-block`)가 과거 시각으로 찍혀 **탐지 창(최근 15분) 밖으로 이탈** → `card(rule)`이 3이 아닌 2에 머물러 임계(>2)를 못 넘겼다. 포털 시계 기준인 S1·S4·S8은 영향이 없었다.
- **해결:** pfSense 시각을 호스트와 동기화(`ssh admin@10.10.30.1 "date $(date +%Y%m%d%H%M.%S)"`). **OpenVPN보다 먼저** 시계를 맞춰야 터널 상태가 흔들리지 않음을 확인.
- **결과:** `pfsense-block`이 현재 시각으로 OpenSearch에 수신되고, `.22`에 대해 3종 rule이 한 창에서 상관돼 S10 이벤트가 매 1분 정상 발화. 기동 체크리스트에 "pfSense 시계 먼저 확인" 항목 추가.

### 1-2. 포털 보안 이벤트가 Graylog에 도착하지 않음
- **문제:** 포털은 HTTP를 정상 응답(404/401)하는데, 그 `web.request`/`web-scan`/`login-bruteforce` 이벤트가 Graylog에 20분간 1건밖에 안 들어왔다.
- **원인:** 시계 교정에 따른 OpenVPN 재연결로, 포털→Graylog GELF TCP(`10.250.0.2 → 10.250.0.100:12201`)가 **반쪽짜리 좀비 소켓**(상태는 `ESTAB`이지만 `Send-Q`에 4.5KB 적체, 미배출)으로 남았다.
- **해결:** 포털 백엔드 재시작(`sudo systemctl restart haedam-portal.service`)으로 새 GELF 연결 수립.
- **결과:** 이벤트 전송 재개 확인. **터널 재시작 뒤에는 포털 백엔드도 재시작**해 GELF를 다시 붙이는 것을 체크리스트에 반영.

### 1-3. S7 자동 복구(Active Response)가 호출되지 않음 — 팀에서도 미완이던 부분
- **문제:** 홈페이지 변조 시 Wazuh FIM은 탐지하는데 복구(AR)가 자동 실행되지 않았다. (팀 프로젝트에서도 끝내 자동 호출을 완성하지 못한 지점)
- **원인:** `active-response`의 `location`을 `specific`+`agent_id`로 넣어 Wazuh 4.9가 거부(`ERROR (1302): Invalid active response location: 'specific'`). 또한 매니저가 재시작 시 `ossec.conf`를 덮어써, 컨테이너 내부가 아니라 **마운트된 호스트 설정 파일**을 고쳐야 했다.
- **해결:** `location:local`(보고 에이전트에서 실행, 에이전트 ID 무관) + `rules_id 554,550`으로 바꾸고, `infra/wazuh/config/wazuh_cluster/wazuh_manager.conf`(마운트 원본)에 등록. agent 재시작으로 `ar.conf` 반영.
- **결과:** 변조 발생 **0.1초 내**에 `run=ar`로 기준본 해시 복구, `verify ok`. **사람 손 없이 복구 1회**라는 목표 달성.

### 1-4. S4 "성공" 로그인이 실패하던 버그
- **문제:** 5실패+1성공 패턴에서 마지막 성공 로그인이 계속 401이 나 패턴이 만들어지지 않았다.
- **원인:** Windows에서 생성한 비밀번호 파일이 **CRLF**라, Kali로 전송된 비밀번호 끝에 캐리지리턴(`\r`)이 붙어 자격 증명이 어긋났다.
- **해결:** 전송 시 `tr -d '\r\n'`으로 CR 제거. 자격 증명 유효성(단일 로그인 200)을 먼저 검증한 뒤 공격 실행.
- **결과:** 5×401 + 1×200 패턴 정상 생성 → S4 탐지 발동 → 계정 잠금·세션 회수 → 비번 재설정 복구 → 티켓 종료.

## 2. 설계·구조에서 배운 점
- **멱등성과 티켓 생명주기:** 같은 조치가 중복 호출돼도 안전하도록 멱등 키를 쓰고, `open→responding→verified→restored→closed` 상태로 전 과정을 추적하면 "적용했지만 아직 안 풀린 조치" 같은 상태를 명확히 관리할 수 있었다.
- **가용성 우선 판단(S12):** 폭주를 탐지해도 **헬스체크로 실제 저하가 없으면 차단하지 않는(no_action)** 설계가, 정상 사용자 오차단을 막는 올바른 선택임을 실측(p95 36.8ms)으로 확인했다.
- **계층 간 결함 추적:** "이벤트가 상관되지 않는다"는 증상 하나에서 시계·소켓 같은 **인프라 계층의 근본 원인**까지 내려가 본 경험이, 단일 구성요소가 아니라 파이프라인 전체를 보는 눈을 길러줬다.

### 3-2. 개인 포트폴리오 제출 후 강사 피드백
- **좋았던 점:** 6개 시나리오를 PC 1대로 재구성해 공격→탐지→자동대응→복구까지 실제로 동작시킨 점, 실측 수치(탐지→차단 3.7초·오차단 0건), 시계·GELF 소켓 문제를 원인까지 추적한 점, `MY-WORK.md`·`CREDITS.md`로 작업 범위를 나눈 점.
- **보완 1 — 저장소가 밖에서 열리지 않음:** 비공개 상태였다. → **반영:** 공개 전환 전에 Git 이력 전체에서 실제 비밀값을 검사했다. 남은 것은 Wazuh 공식 기본 계정값뿐이다(실습망 VPN 주소에만 바인딩). 개인정보(연락처·생년월일·주소)도 없음을 확인한 뒤 공개로 전환한다.
- **보완 2 — 이력서 캡스톤 칸에 1인 재구현 결과 추가:** → **반영:** "6/6 시나리오 1인 재구현·실측(2026-11-16), 팀 미완 S7 자동 복구 완성" 한 줄을 추가한다.
- **보완 3 — 이력서 개인정보 노출 주의:** → **반영:** 이력서·자기소개서는 저장소에 두지 않고 비공개 제출만 한다. 저장소 추적 파일과 발표자료(PPT/PDF)에 개인정보가 없음을 확인했다.

## 4. 더 있었다면 개선하고 싶은 것
- **S10 pfSense 경계 차단 재조정:** 현재 경계 차단은 재조정(reconciliation) 단계에서 한계가 있어, pfSense 응답 도구의 소유권·해제 흐름을 더 견고히 다듬고 싶다.
- **S12 판정 지표 고도화:** `/health` 2000ms 기준 대신 정상 사용자 경로(`/login` 등) 지연을 지표로 바꿔, 실제 서비스 저하를 더 민감하게 포착.
- **Graylog 알림 grace 조정:** S8·S10이 알림을 공유해 grace(15분)가 자동 전달을 지연시키는 경우가 있어, 케이스별 알림 분리 또는 grace 재설계.
- **기동 자동화:** 시계 동기화·GELF 재연결 등 체크리스트 항목을 기동 스크립트 하나로 묶어 "한 번에 올리고 바로 실측".

## 5. 느낀 점
팀에서는 C 자리(Wazuh·S7·티켓 저장소·대시보드)만 깊게 봤는데, 혼자 PC 한 대에 전부 올려보며 **네트워크 경계부터 탐지·자동화·서비스까지 한 흐름으로 이해**하게 됐다. 특히 "팀에서도 못 끝낸 S7 자동 복구"를 직접 완성하고, 재검증 중 숨어 있던 환경 버그(시계·소켓)를 증상에서 근본 원인까지 추적해 고친 경험이 가장 크게 남는다. 보안 자동화는 "탐지만" 되는 게 아니라, **오작동 없이 끝까지(대응·복구·종료) 도는 것**이 핵심이라는 걸 체감했다.
